# 仮想通貨Botのバックテスト：プロフィットファクターと最大ドローダウンで何がわかるか

Botを作ったはいいけれど、「これは本当に使えるのか？」と判断する方法がわからない——そんな悩みを持つ方に向けて、バックテストの基本的な考え方と、特に重要な指標である**プロフィットファクター（PF）**と**最大ドローダウン（MDD）**の読み方を解説します。

---

## バックテストとは何か

バックテストとは、過去の価格データに対してBotの売買ロジックを適用し、「もし過去にこの戦略を動かしていたら、どんな成績になったか」をシミュレーションすることです。

なぜ必要かというと、**実際の資金をリスクにさらす前に戦略の有効性を検証できる**からです。

ただし、バックテストには重要な前提があります。**過去の成績は将来の成績を保証しない**という点です。バックテストはあくまで「過去データに対してはうまくいった」という証拠であり、将来も同じように機能するとは限りません。この点を常に念頭に置いておく必要があります。

---

## インサンプル（IS）とアウトオブサンプル（OOS）の違い

バックテストで最も重要な概念のひとつが、**インサンプル（IS）**と**アウトオブサンプル（OOS）**の区別です。

### インサンプル（IS）
パラメータの最適化に使うデータ期間です。例えば2023年1月〜2024年12月のデータを使って「このパラメータが最も良かった」と決めるための期間です。

### アウトオブサンプル（OOS）
最適化に使わなかった検証用データです。例えば2025年1月〜2025年12月のデータで、ISで決めたパラメータが「見たことのないデータ」でも通用するかをテストします。

なぜOOS検証が重要かというと、ISだけで評価するとパラメータが過去データに過剰に合わせられた（カーブフィッティングした）戦略を誤って「良い戦略」と判断してしまうからです。

**目安として、IS取引数30件以上、OOS取引数10件以上**を確保することを推奨します。取引数が少なすぎると統計的に意味のある評価ができません。

---

## プロフィットファクター（PF）の読み方

**プロフィットファクター（PF）**は、バックテストで最もよく使われる収益性の指標です。

```
PF = 総利益 ÷ 総損失（絶対値）
```

例えば、総利益が15万円、総損失が10万円であれば、PF = 1.5 となります。

### PFの目安

| PF値 | 評価 |
|------|------|
| 1.0未満 | 赤字（使用不可） |
| 1.0〜1.2 | 損益トントン〜微益（リスクに見合わない） |
| **1.2以上** | **実用的な最低ライン** |
| 1.5以上 | 良好 |
| 2.0以上 | 優秀 |

IS期間でPF = 1.2以上、かつOOS期間でも PF = 1.1以上 を確認できれば、一応「本番に出せる候補」と考えられます。

### 注意点：手数料込みで計算する

PFを計算する際は、**取引手数料を必ず含めた値で評価**してください。例えばGMOコインのTakerフィーは0.05%です。手数料なしのバックテスト結果は現実から乖離しており、参考になりません。

---

## 最大ドローダウン（MDD）の見方

**最大ドローダウン（MDD）**は、バックテスト期間中に資産が最高点からどれだけ下落したか（最大の谷の深さ）を示す指標です。

```
MDD = (資産の最高値 - 最大の谷の値) ÷ 資産の最高値 × 100 [%]
```

例えば、資産が10万円のピークから7万円まで下落した場合、MDD = 30%です。

### MDDが重要な理由

PFだけが良くても、途中で壊滅的な損失が発生するBot は実用に耐えられません。MDDは「最悪どれだけ損するか」を示す指標です。

**実運用の目安としては、MDD -20%以内を一つの基準**にすることが多いです。ただし、これはBot戦略や資金量によって異なります。

### IS/OOSでMDDを比較する

重要なのは、**IS期間のMDDよりOOS期間のMDDが極端に悪くなっていないか**を確認することです。IS=5%、OOS=40% のような乖離があれば、ISに過剰最適化されている可能性があります。

---

## 過剰最適化（カーブフィッティング）を避けるコツ

バックテストで陥りやすい罠が**過剰最適化（カーブフィッティング）**です。パラメータを徹底的に最適化すると、過去データにはぴったり合うのに、将来のデータでは機能しない戦略ができあがります。

### 避けるための実践的なコツ

**1. パラメータ数を最小限に保つ**
パラメータが多いほど過去データへの当てはまりは良くなりますが、過剰最適化のリスクも増します。「本当に必要なパラメータか？」を常に自問してください。

**2. IS:OOS = 7:3 が一般的な分割比率**
データ全体の70%をISに、30%をOOSに使うのが一般的です。この比率は絶対ではありませんが、OOSが少なすぎると検証の意味が薄れます。

**3. ロバスト性チェック**
最適パラメータの周辺値（例：移動平均20期間が最適なら、18・19・21・22期間）でも同程度の成績が出るか確認します。最適値だけが飛び抜けて良い場合は過剰最適化を疑ってください。

**4. 複数の時期でOOS検証する**
OOS期間を変えてテストし、複数の「見たことのない期間」でも安定した結果が出るかを確認します。

## ペーパートレードで実環境検証

バックテストをクリアしても、実際の取引環境では様々な問題が起きることがあります。

- **スリッページ**：注文価格と約定価格のズレ
- **板薄問題**：出来高が少ない時間帯の約定困難
- **APIの遅延・エラー**：実際の通信は理想的ではない

そのため、本番資金を投入する前に**ペーパートレード（仮想資金での実稼働テスト）**を一定期間実施することを強く推奨します。

バックテストは「過去データでの検証」、ペーパートレードは「現在進行形の市場での検証」です。この2段階を経ることで、本番投入時のリスクを大幅に減らせます。

## まとめ：バックテストで確認すべき最低ライン

バックテストで最低限確認すべき条件をまとめます。

| 指標 | 最低ライン |
|------|----------|
| IS取引数 | 30件以上 |
| OOS取引数 | 10件以上 |
| IS PF | 1.2以上 |
| OOS PF | 1.1以上 |
| MDD | -20%以内（目安） |
| IS/OOS MDD乖離 | 2倍以内（目安） |

これらはあくまで目安であり、戦略の種類や運用資金によって適切な基準は変わります。重要なのは、**自分なりの明確な合格基準を事前に決めておき、その基準を一貫して適用する**ことです。
